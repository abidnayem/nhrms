# Personnel Lifecycle Audit and Delivery Plan

Audit date: 2026-10-13
Baseline branch: `main`
Baseline working tree: clean (`main...origin/main`)

## Existing system

### Structure and dependency flow

The solution is `NHRMS.slnx` with five .NET 10 projects and a separate Angular 22 SPA. The intended dependency direction is Domain <- Application <- Infrastructure/API: Domain owns entities; Application owns feature services, DTOs, and repository/Unit of Work contracts; Infrastructure implements those contracts with EF Core; API controllers call Application services. The Angular app calls the API directly through `HrmsApiService`.

Infrastructure currently groups EF Core context, entity configuration, Unit of Work, and all repositories in `NHRMS.Infrastructure/Class1.cs`. Application also has a single `Class1.cs` for its abstractions. This works but differs from the more organized feature folders used elsewhere.

### Existing entities and persistence

`Company`, `Branch`, `Department` (including parent/child), `Designation`, `EmploymentType`, and `Employee` are in `NHRMS.Domain/Class1.cs`. Employee currently stores company, optional department/designation/employment type, code, names, email, joining/leaving dates, active flag, and inherited soft-delete/audit timestamps and user names. Attendance, leave, payroll, role/permission, user account, and user-role entities live in `HrModules.cs`.

EF Core SQL Server is configured in `NhrmsDbContext`; existing migrations use a non-destructive migration history, company-scoped unique codes, a SQL employee-code sequence, and `NoAction` relationships to avoid SQL Server cascade-path failures. `Repository<T>` soft-deletes and filters deleted rows. `UnitOfWork` calls `SaveChangesAsync`. `Program.cs` automatically migrates and seeds at startup; this is a material deployment risk outside development.

### APIs, services, and Angular

CRUD-style API controllers and Application services exist for employees, companies, branches, departments, designations, employment types, attendance, leave types/requests, payroll cycles, roles, and users. Employee API currently has only unfiltered list and create. Employee codes are generated from the SQL sequence (`EMP-000001` format). Employee creation checks company existence, names, and joining/leaving order, but not reference ownership/activity, required joining date, or email syntax. Department/designation/manager and employment type are not returned consistently by the employee DTO.

The standalone Angular SPA has overview, employee roster/form, attendance, leave, payroll, and access pages, using template-driven forms, basic loading/error states, and `HrmsApiService`. Employee list loads all employees without pagination or search. No lifecycle timeline, onboarding, contracts, probation, career changes, discipline, separation, document management, or approval UI is present.

### Security, audit, and tests

Entities inherit `CreatedAtUtc`, `UpdatedAtUtc`, `IsDeleted`, and nullable `CreatedBy`/`UpdatedBy`; current services commonly hard-code `CreatedBy = "system"`. Roles and permissions are stored, but there is no authentication middleware, claims-based actor identity, authorization policy, or API `[Authorize]` boundary. Do not expose disciplinary or compensation workflows until server authorization is implemented.

The test project has 11 xUnit unit tests using in-memory repository fakes. No API integration tests or Angular tests cover lifecycle flows. Baseline `dotnet test NHRMS.slnx --nologo -m:1` passed: 11 passed, 0 failed. Existing restore/build reports NU1903 high-severity advisories for transitive `System.Security.Cryptography.Xml` 9.0.0. Baseline Angular `npm run build` could not start under the restricted process sandbox (`spawn EPERM`); this is an environment limitation, not an observed source compilation failure.

## Risks and decisions

- Local bearer authentication now protects the API; the one-time bootstrap secret and JWT key must be configured securely. JWT role/permission claims remain valid until their 60-minute expiry when assignments are changed.
- Hiring, confirmation, compensation eligibility, approval authority, statutory rules, document retention, termination authority, final-settlement calculations, and rehire policy are business-specific and must not be guessed.
- Recruitment, file storage, notification, payroll settlement, and account-revocation providers are absent; integrate through contracts rather than copying their business logic.
- Development API startup applies EF migrations and seeds data. Production startup does not; production migration and seeding is available only through the explicit `--migrate-and-seed` command. No migration has been applied to the configured database during this audit.
- Employee code sequence is database-global while uniqueness is company-scoped; acceptable but should be made configurable only when the numbering policy is decided.
- The web build and API smoke test depend on local process permissions and a reachable SQL Server. Angular process spawning was denied by the default sandbox at baseline.

## Work completed in this increment

Phase A employee-organization integrity: `EmployeeService` now rejects missing joining dates, malformed email addresses, inactive companies, and department/designation/employment-type references that are inactive or belong to another company. A supplied leaving date creates the record inactive. The employee DTO and existing Angular form/roster now carry and display employment type.

The employee directory now also has a separate paginated search endpoint with name/code/email search, company/department/status filters, stable ordering, and a page-size limit; the Angular roster consumes it and exposes those filters. The original unpaged GET endpoint remains available.

Phase C has started with a standalone onboarding checklist: required tasks cannot be waived, tasks can only leave `Pending` once, and task creation is limited to active employees. The API and Angular page are wired to the existing employee feature. EF migration `20261013154310_AddEmployeeOnboardingTasks` adds the task table, relationship, and due/status index. It was reviewed and generated but not applied to a database.

Phase D now has a probation case and review workflow. HR can start one open probation per employee; reviewers submit a reasoned Continue, Extend, or Confirm recommendation; a different authorized actor must approve or reject it. Approval records both actors/timestamps, and accepted extensions/confirmations update the case. The Angular probation page and permission checks are wired. EF migration `20261013160206_AddProbationWorkflow` adds probation cases/reviews and filtered uniqueness constraints; it was reviewed and generated but not applied. Confirmation letters, reminders, and due reports still need document/notification services and business policy.

Phase E now covers approved effective-dated changes to the organization assignments represented by the existing Employee entity: department, designation, and employment type. Requests retain the previous and proposed values, reason, requester, decision, and apply timestamp. A requester's own approval is rejected, one pending/future-approved change is allowed per employee, and future-approved changes remain staged until explicitly applied on/after the effective date. The API and Angular history/request/approval screen are wired. EF migration `20261013163444_AddEmploymentChangeWorkflow` creates the history table and open-request uniqueness index; it was reviewed and generated but not applied. A production scheduler/outbox for applying due changes is not present; the UI/API currently expose explicit application.

Phase F now has a restricted employee-relations case workflow for show-cause, warning, investigation, and other record types. A separate permission set controls read, case creation, and decision; the opener cannot decide their own case. The UI is on a dedicated route, and the API does not expose case details through general employee reads. EF migration `20261013163951_AddRestrictedDisciplinaryCases` adds the case table and employee/date index; it was reviewed and generated but not applied. This remains a basic case record: evidence storage, investigation tasks, retention, audit of reads, and jurisdiction-specific action types remain outstanding.

Phase H now includes JWT bearer authentication, 600,000-iteration PBKDF2 password hashes with login-time upgrade of legacy SHA-256 hashes, a rate-limited one-time bootstrap endpoint, seeded role permissions, per-controller API authorization, an Angular sign-in/setup screen, session-scoped token storage, and permission-aware route/navigation handling. Employee and onboarding writes record the authenticated actor. Production requires a configured JWT key; API keys are not stored in tracked settings. Production migrations are opt-in through the documented command; Development startup still migrates and seeds automatically.

Verification after changes: .NET solution build succeeded; .NET test suite passed 27/27; Angular production build succeeded; EF reports no model changes pending; `git diff --check` reported no whitespace errors. Restore continues to report the pre-existing NU1903 advisories described above. EF migration scaffolding previously attempted to create a duplicate probation migration against a stale build snapshot; the duplicate un-applied scaffold was removed and subsequent model/migration alignment was confirmed offline. The configured SQL Server could not complete its encryption handshake, so migrations were not applied and database-backed API smoke testing remains outstanding. The web app returns HTTP 200; the API returns HTTP 200 for `/health` and Development OpenAPI, and protected employee/discipline routes return HTTP 401 without a bearer token. API and Angular dev servers are running on localhost ports 5209 and 4200, respectively, with the API started using `--skip-startup-migrate` so startup does not apply schema changes.

Remaining scope is substantial: employee profile/contact/document data, recruitment handover and document verification, compensation/contract/grade/branch/manager changes, disciplinary evidence and retention, separation/clearance/settlement, reports, and API/Angular integration tests remain for subsequent phases. Sensitive workflow approval roles, termination authority, compensation rules, document retention, final-settlement calculation, and rehire policy remain business decisions and were not guessed. This increment is not a complete lifecycle module.
